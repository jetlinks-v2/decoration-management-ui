# 装修管理

JetLinks 2.20 装修管理模块，PC 使用 SaaS runtime-ui 宿主；H5 独立构建，两端访问同一装修服务。公共基础页面由 `property-base-ui` 唯一提供，调用基础档案 `/property/**`，装修业务统一调用 `/decoration/**`。

## 开发与构建

使用 Node 22.18+、pnpm 9.9。PC 通过 Git 子模块检出到 `runtime-ui/modules/decoration-management-ui`，跟踪 `2.20`，具体版本由宿主 gitlink 固定；不使用本机绝对路径软链接。先在宿主执行 `git submodule update --init -- modules/decoration-management-ui modules/property-base-ui`，再由宿主安装依赖并启动。源码仓库中可将 `node_modules` 链接到宿主依赖目录；该链接不提交。不要在共享依赖的源码目录运行自动安装命令。

在宿主目录运行：

```sh
pnpm --filter jetlinks-web-core dev -- -- --module-name decoration-management-ui,property-base-ui,authentication-manager-ui
pnpm --filter jetlinks-web-core build -- -- --module-name decoration-management-ui
```

在本仓库运行：

```sh
node --test tests/*.test.mjs
./node_modules/.bin/vue-tsc --noEmit -p tsconfig.mobile.json
./node_modules/.bin/vite --config vite.mobile.config.ts
./node_modules/.bin/vite build --config vite.mobile.config.ts
```

PC 产物为 `dist/`，H5 产物为 `dist-mobile/`，H5 默认部署到 `/decoration-h5/`。独立开发端口9401，`/api`默认代理本机8844；当前测试环境联调由被忽略的PC本机配置在9302同源提供H5构建制品，并沿用PC已有认证和本地8505业务代理，不另占H5端口。独立构建显式配置平台认证头`X-Access-Token`，不依赖PC宿主.env。H5 不加载桌面布局。

PC 类型配置使用子模块相对路径引用宿主的 `../../tsconfig.base.json` 和同级 `property-base-ui`；请在上述子模块位置执行 PC 类型检查。整体类型检查也会加载宿主源码，必须区分宿主既有错误与本模块错误，不将构建成功当作全仓类型检查通过。

附件和签名上传期间，配置、申请和办理表单暂停保存并阻止切换项目、路由或离开页面；同一表单全部并发上传结束后恢复操作。签名从图片生成开始计入，失败释放本次状态，旧编辑对象的晚到回执不会写回新表单。

装修 PC 的申请、详情、任务、自检和各类基础配置，以及 H5 房屋切换，统一使用页面弹窗。关闭或取消弹窗直接丢弃未保存草稿，不再弹出二次确认；上传、提交及结果待核对时仍阻止关闭。应用内切换页面或项目时保留未保存内容确认，不使用会暂停页面的原生 `window.confirm`。关闭或刷新浏览器时仍保留未保存内容保护。

本地同时使用 SaaS 租户入口和应用入口时，装修专用 Vite 配置应使用 `VITE_APP_RUNTIME_SCOPE=auto`。固定项目模式 `project` 必须提供项目编码；不能将业务应用 ID 当作租户编码。进入应用前确认当前会话、应用和基础档案属于同一租户。

连接测试公共服务时，在被忽略的本机代理配置中区分三条路径：`/api/decoration/**` 去本机装修 HTTP 8505；`/api/property/**` 经测试网关显式服务路径 `/property-base-service/property/**`；其余公共 `/api/**` 经 `/all-in-one-service/**`。显式公共服务路径可以避免历史自动发现路由将 `/system/**` 等初始化请求错误分发至独立业务服务。装修信息请求仍需携带当前登录与应用上下文，不能以固定令牌、租户 ID 或服务路由代替授权。公共服务名称以目标环境实际注册结果为准。

装修资料配置编辑使用居中弹窗，所属项目、房屋类型和装修类型控件等宽。资料与图纸分别在表格内维护：资料设置名称、模板与启用，图纸设置名称、必填与启用。全部装修基础配置按项目、房屋类型、装修类型及场景识别，不再提供配置名称输入、列表列或筛选，也不生成内部名称；装修协议不再提供主协议标题输入，新增协议沿用固定文书标题；资料名称和检查项名称仍用于业务内容。关闭资料弹窗直接丢弃草稿，上传、保存中或结果待核对时仍禁止关闭。 相关行为测试覆盖无名称保存、草稿关闭及分组增删。完整类型检查仍受宿主既有错误影响。

装修资料配置沿用原通邑系统的固定项目：消防责任书、装修须知、服务协议、申请表确认，以及拆改图、原始平面图、水电气图、效果图、业主身份证正反面。新增和编辑草稿自动补齐缺项，固定名称与删除受限，启用及图纸必填可调整；效果图默认非必填。已有同名项目保留ID、附件回执和设置，自定义项目保留。四份原版Word空白模板位于 `assets/material-templates/`，保存时通过当前项目的私有模板附件接口登记，PC/H5申请继续从配置回执读取；不在新系统运行时依赖原系统存储或鉴权。打开弹窗不会直接改写已保存配置和历史申请，补齐后须保存才生效。

## 业务初始化

装修服务部署在 `property-management/services/property-decoration-service`，基础档案服务是运行前置。为业务项目准备：

基础档案与装修共用主数据：组织树中标记为 `project` 的节点是装修项目；空间管理中的末端房屋及其房屋资料是装修房屋；客户管理中的客户和有效客户房屋关系是装修申请人、业主及办理关系来源。员工档案用于审核、巡检和验收人员，不能替代客户房屋关系；装修不另建一套项目、用户或房屋主档。首验、二验人员下拉按当前应用有效成员、有效启用员工、候选人具有申请所属项目数据权限三项筛选。候选查询必须带目标项目，项目切换会清理旧人选，提交指派由后端再次核验；打开弹窗加载当前应用范围的候选，并支持姓名搜索；人员过多时要求缩小姓名搜索，查询失败与无匹配员工分别提示。

所有项目筛选统一使用组织架构树，保留组织层级并按名称搜索；仅 `organizationType=project` 节点可选，其他组织置灰且只能展开。业务页使用装修目录转发的基础组织树，客户、房屋页直接读取公共组织树；选择事件再次校验节点，不按名称或是否叶子推断项目。

1. 组织标注为项目，绑定根空间，完善房屋资料与 SaaS 客户账号关联。
2. 维护房屋类型和客户性质字典；办理资格来自有效客户房屋关系，不能以姓名或电话推导资格。PC 和后端均取消额外的「办理关系」配置依赖；有效客户房屋关系、员工身份及项目范围校验仍保留。
3. 配置项目+房屋类型的协议与收费科目；配置项目+房屋类型+装修类型的材料；巡检与验收内容先在页面外侧选择检查场景、所属项目、房屋类型和装修类型，再点击“配置检查内容”。弹窗继承并只读展示该范围，先维护巡检分类，再维护分类下的检查项；同范围已有配置时打开原配置，不重复新建。分类名称、分类排序统一作用于组内检查项，保存沿用既有检查项结构，保留检查项ID和参考附件。空分类须补充检查项或删除，重复分类名不能保存；没有检查分类时仍可显式保存空检查配置。需要空材料时也应显式保存配置。
4. 配置备案有效期；未配置时沿用三个月默认值。所有业务申请、材料和任务保留配置快照。

PC「装修基础配置 → 巡检与验收内容配置 → 导入检查配置」提供19列Excel模板及逐行错误反馈。项目按当前有权项目名识别，房屋类型使用公共启用字典编码或文案；按文件内维度整批合并，同分类同名项更新、未导入项保留。仅接受xlsx、最多1000行/10MB，图片须嵌入工作簿，单项一张JPG/PNG且不超过2MB。校验失败整批不保存；公共字典命令缺失时明确报错。提交超时先只读核对原收据，未发现成功收据时仅允许显式重试原文件/原请求号；未知结果或进行中禁止换文件、切换项目和离页。正常结束后刷新当前配置列表。

菜单资源位于 `baseMenu.json`；宿主路由 code 必须与 `views/decoration/**/index.vue` 一致。PC 员工、审核、指派和业主本人是不同办理资格。H5 只允许认证本人有效房屋关系；具备管理查询权限不能替代业主资格。

菜单授权保留“装修管理”根节点（`decoration-business` / `decoration/business`），原子菜单 ID、路由与按钮权限不变。仅在独立装修应用的导航中通过 `getMenuFilters` 展开根节点；项目上下文及无应用上下文保留完整树，不修改 SaaS 平台代码。已有环境需通过菜单初始化同步根节点及父子关系，源码更新不会直接重写数据库菜单。

独立装修应用内的业务入口继续作为一级菜单：装修概况、装修基础配置、装修自检表、在线审核、装修备案证明、装修巡检、首次验收、二次验收、装修记录。装修基础配置下设四个独立二级菜单：装修协议、装修资料配置、巡检与验收内容配置、备案有效期；不再显示配置类别Tab或办理关系入口。装修巡检显示“分配巡检任务”“巡检记录”“违规记录”三个已授权入口。分配页维护角色和周期；巡检记录每次周期任务一行，合并待巡检、正常结果和整改复核状态，按项目、房号及更新时间范围筛选，更新时间包含反馈及整改的最新变更。详情同时读取原任务及其反馈、重发整改记录，保留附件和操作轨迹，不再区分任务/记录Tab；分配页行内入口复用同一列表并固定装修ID。底层任务与反馈独立保存，个人任务与集中违规入口不变。已有菜单及按钮授权不自动改写，去巡检需要提交检查结果的按钮权限与当前任务角色资格。宿主公开菜单扩展提升旧装修分组并归并巡检入口；旧配置页的四个已授权类别沿用同一页的原权限与按钮拆成导航，新资源按类别声明权限，其他业务菜单保持原状。

在线审核复用新增申请表单及既有创建授权，装修记录不再显示新增按钮。在线审核和协议、资料、备案有效期配置页面无需先选列表项目即可打开新增弹窗，在表单内选择组织树中的项目；列表项目已选时作为初始值，表单选择不改变列表范围。巡检与验收内容配置先选完整外侧范围，弹窗沿用所选范围。保存配置仍要求所属项目，切换草稿项目重建内容，避免携带原项目附件；上传与未知结果保护继续有效。


## 支付、财务与消息

未配置真实适配器时，缴费、退款、通知发送明确返回不可用，不产生成功状态。未核验收款不能发证；手动结束不会标记退款成功。财务适配器必须核对应用、租户、项目、房屋、主体、科目、资金方向、线上/线下类型、金额、真实状态与唯一单据；消息必须取得真实受理回执。

接入契约为后端 `DecorationFinanceGateway` 和 `DecorationNotificationGateway`。退款在二次验收通过后按申请冻结协议的退款总额一次性办理，成功后自动结束；未配置总额时退还实收保证金。历史两期配置合并为总额并扣除已核验退款，首验后不开放退款。首验/复验、整改和巡检的保存不表示推送已送达。资金核验相关操作在接口接通和真实联调之前保持不可办理。

经授权的本机测试可显式启用后端模拟提供方：`DECORATION_INTEGRATIONS_SIMULATED_ENABLED=true`，默认关闭。模拟服务沿用真实业务接口、权限与状态机，回执持久化并标记 `SIMULATED_DECORATION`；能力接口返回 `simulated=true` 时详情展示提示。不产生真实资金交易或实际通知，模拟验收与真实财务/消息接入分别记录。

组织配置在组织类型保存为项目后显示项目章维护入口，支持 PNG/JPEG 上传、更换、移除及私有预览。装修按申请所属项目经公共组织目录和平台文件能力读取章。客户房屋及 `house-type` 字典均复用公共档案，不重复建立主数据。

## H5 接入

H5 员工端、业主端通过独立地址 `/decoration-h5/?side=staff`、`/decoration-h5/?side=owner` 访问，装修概况不展示 H5 入口按钮。两端沿用当前应用及租户入口选择，不在URL传递登录凭据。独立浏览器页面使用装修自己的登录页和标签页会话，支持 SaaS 图片验证码、安全校验及按平台配置加密密码，不读取 PC 登录凭据。员工端调用员工装修接口并从本人装修菜单读取操作授权，业主端继续使用本人专属接口；入口参数不能授予员工资格或业主关系。员工端不提供业主新增申请。

浏览器可从 SaaS 应用入口打开；链接仅携带 `projectCode` 会话入口和 `applicationScope` 应用选择，不携带令牌与用户身份。APP 注入的 `window.decorationHost` 是待对接契约，详见 [H5 与 SaaS APP 接入定义](docs/装修H5与SaaS_APP接入定义.md)。


正式网关、APP Bridge、真机、支付/财务/消息均需要对应环境联调。源码行为测试、数据库测试与浏览器测试不能替代这些验收。

业务依据与逐页对照见 [重写功能清单](docs/装修JetLinks重写功能清单与实施计划.md) 与 [PC/H5 功能对照](docs/装修PC-H5新旧系统功能与细节对照.md)。私密交接文档、令牌和本机配置不进入仓库。

PC装修巡查提供“巡查指派”和“日期任务”页签：从已发证申请指派多个角色，每个角色独立设置“每N天一次”，并选择整改复核角色。服务端生成独立自然日任务，当天到期角色共享办理；不会把间隔天数当作计划总次数。已生成任务保留当时的角色和检查项。角色候选需要认证公开角色命令、模板角色资产策略及应用可用角色绑定；外部目录故障明确报错。

## 公共基础模块

PC 宿主须检出并加载 `modules/property-base-ui`（分支 `2.20`）。开发白名单包含本业务模块、`property-base-ui` 和认证模块；`build` 输出独立业务包，`build:with-base` 输出包含公共模块的宿主聚合产物。基础菜单仅由公共模块初始化一次，不再初始化本业务的旧基础菜单。已有角色须授权公共 `charging/*` 菜单，旧菜单编码不会自动迁移；仅清理对应应用的旧基础菜单，勿全量重建其他系统菜单。项目章只在公共组织配置中维护：`PUT /property/organization/{id}/project-seal?version=...` 受控上传并保存，`DELETE` 同路径移除，使用独立 `seal` 权限。装修只读当前项目章，不走通用上传后跨服务绑定文件引用。

资料审核按装修图纸、装修资料分表逐项展示状态、审核人、时间和备注，每行独立查看、下载、审核；保证金单独审核。申请仅提交已上传的资料和图纸，空选填项保留在配置快照中，显示“未提交”且不提供空查看或审核入口，不阻塞审核完成。图片支持框选、编辑/删除批注及保存批注图片后提交。附件查看和下载分开：PDF/图片本地预览，DOCX排版预览，XLS/XLSX按工作表查看（预览最多2000行/100列，下载保留完整原件），旧DOC显示正文预览。私有附件元信息和正文沿用下载的应用、租户、项目及申请权限，不外发文件地址。新申请自检整表独立审核并支持驳回后重传，历史申请不补造审核记录。

PC装修详情以单次申请的六步办理流程组织：装修申请 → 费用缴纳 → 装修备案证明 → 首次验收 → 二次验收 → 退费申请。左侧展示每步真实状态，右侧展示该步骤内容和有权动作；申请内分申请信息、图纸与资料审核，缴费和退款各自展示凭据。装修巡检、操作轨迹在左侧独立保留，巡检和首验/二验分别按服务端任务类型过滤并分页。在线审核入口定位申请的审核区，备案入口定位备案证明，巡检/违规入口定位装修巡检，首验/二验分别定位各自阶段，装修记录定位申请信息。刷新、办理回执保留当前步骤；切换步骤/分区遵守未提交内容确认及上传、未知结果保护。顶部只保留房屋、业主、申请编号和状态摘要，计划/实际结束等动作放入更多操作。

## 装修移动端

业主端底部导航包含“装修申请、装修记录、装修通知”。申请页顶部下拉选择本人有效关联房屋，新申请带入所选房屋；下方分页展示当前房屋本人有权的未办结申请，点击记录卡或“查看办理进度”进入六步流程，返回后保留房屋选择。二验通过且退款成功的申请从此处移除，但仍保留在全部装修记录中；房屋由其他登记账号占用而本人无权查看申请时，提示联系物业核对办理账号，不放开其他账号或应用的数据；房屋已在办理中时新增入口禁用，显示“装修办理中”；点击申请前重新核验占用，回到首页时从服务端更新统计，不用某一笔历史申请的结束覆盖整套房屋状态。二次验收通过且退款成功才算装修结束。记录和通知均独立分页读取本人全部有权申请摘要，不按首页选房筛选；通知页通过 `POST /decoration/mobile/applications/_notifications/_query` 读取真实业务节点通知，展示当时的内容及通知时间，点击进入对应申请的办理步骤；不以当前申请摘要虚构通知历史，不回填上线前的旧事件。PC/H5详情及六步流程均展示当前下一步提醒，并提供前往对应步骤的入口。审核全部通过、缴费完成、备案完成、首验/二验通过及退款结束依次引导下一步，未通过或等待办理显示对应处理要求。通知深链仅带 `applicationScope`、`decorationId`、`step`，正常登录后仍经过原本人详情权限核验。公共站内信使用现有 `SendUserNotificationCommand`，PC消息中心通过模块公开扩展点展示详情入口；微信订阅消息与APP系统推送需现有平台提供对应通道，不能把站内信当作微信送达。进入流程后返回原页签。首页只统计“我的房屋”和“装修中”，已完成房屋不计入装修中。签署正文、图纸和附件仍在打开申请后读取。六步卡片为：装修申请、费用缴纳、装修备案证明、首次验收、二次验收、退费申请。新申请依次填写「申请信息 → 装修自检表 → 装修图纸 → 逐项资料签署」。自检表沿用原业主端固定九项，逐项是/否（默认“是”），表下签字，保存包含房屋、业主、联系电话、全部答案、签字和日期的完整PNG；汇总状态由服务端计算，修改答案或联系电话需重签。图纸独立上传。资料按当前配置启用项及排序逐项展示完整模板正文、签字并保存整份资料图片，必填资料必须签署，选填可跳过；修改申请信息或模板后需重签对应资料。不再额外展示固定“签署文书”区。固定Word原件下载保持原格式，在线阅读使用同一原件转换的PDF；自定义在线签署模板支持PDF/图片，不能用标题或旧版模板代替正文。PC服务台申请则按「下载自检表/资料模板 → 线下填写签字 → 导入签字文件」办理，自检、装修资料、装修图纸分区，PC不要求在线签名。后端根据来源核验PC自检导入文件或H5自检及实际资料签署，资料/图纸必填项仍由配置决定；私有附件归属及事务规则不变。历史申请保留原有正文、说明和图片，不补造签名。可查看分项审核、驳回重传、备案、验收记录及历史申请。记录详情使用申请自身房屋快照，不受首页选择影响，逐级返回全部装修记录和首页；申请返回首页保留房屋选择，关系失效后清理旧选择。付款、备案和退款分别以服务端回执为准。真实服务模式下，物业代登记的申请仍由 PC 核验财务单据，业主端只显示前台办理提示；业主本人申请保留线上入口。启用模拟服务时，PC/H5 的“模拟缴费 / 模拟退款”按钮调用独立虚拟资金接口，由服务端生成模拟单据，按原审核、验收、金额和本人权限规则流转，测试者无需编造单据号。一次性退款记录按实际结算阶段显示。

申请流程实现位于 `ApplicationForm`、`OwnerApplicationForm` 及 `useApplicationForm/useOwnerApplicationForm`。PC线下文件导入与H5自检、逐项资料签署共用服务端冻结快照和逐项审核规则；审核完成、模拟缴费、打印或下载备案证明、巡检整改、两次验收及一次性模拟退款均由正常页面和业务接口推进。浏览器验收证据和本机运行配置保存在被忽略的运行目录，不随产品发布。PC整体类型检查仍受宿主及 `ChargeItemSelect` 既有诊断影响，应与装修模块诊断区分。

员工端只呈现巡检任务、验收任务和本人办理历史。`POST /decoration/tasks/mine/_query` 从可信员工认证、角色和授权项目筛选后分页；前端不传操作者ID代替本人资格。日常巡检由到期角色办理，验收由指派本人办理，整改复核使用 `taskReview` 按钮授权及任务冻结的复核角色。 巡检指派与整改重指派按钮同时声明公共角色目录的 `role:query` 只读权限，候选仍受当前应用的角色资产范围约束；不授予公共角色的新增、修改或删除权限。员工端不提供申请、审批或任务指派管理入口。

巡检不通过后，直接生成业主可见的整改待办，不再经过整改通知审批；业主提交整改后仍需物业复核。外部消息通知受理与业主任务下发是两项独立结果，任务可见不表示短信或APP推送已经送达。历史办理快照保留原有内容。

两端 H5 的登录及首页采用浅蓝背景与白色圆角卡片，业主端使用房屋插图、员工端使用巡检清单插图（`mobile/assets/`）。插图随构建发布，不依赖外部图片服务；业主六步状态及员工任务、验收、历史页签沿用原业务规则。

## 备案证明打印与下载

备案列表在缴费完成后展示申请，提供施工人员登记、装修备案证明、延期独立入口。人员登记可在发证前独立保存，发证后继续维护人员名单，不改动已发证正文和历史图片；施工人数由登记明细计算。延期仅在到期前七天内或已过期时办理，表单预览原有效期及延期后的截止日期。备案详情分“备案证明”“施工人员”“办理记录”，证件正文、人员名单、发证/打印/下载/延期操作信息分别展示。

备案证明使用装修申请冻结的业主姓名和联系电话，不另设备案人或重复录入电话。窗口提供打印、下载PNG；取消领取登记。首次打印或下载均先将包含项目章的完整PNG上传为装修私有附件，再以回执ID、项目章摘要、输出类型及申请版本归档；成功后自动完成当前版本备案，开放后续巡检与验收。仅打开预览不写入业务。详情显示原图，重复打印与下载复用该版本快照，分别记录操作类型、时间和操作人员，不将发起操作表述为已出纸、已保存到磁盘或已领取。

延期会保留旧版证件图片和操作历史，清除当前版本的打印、下载状态，按新有效期重新打印或下载后完成新版备案。重复输出不得倒退已进入的验收流程。历史领取数据仅只读展示，不要求新记录填写领取人和领取时间；旧版打印记录未带输出类型时按打印展示，不补造缺失图片和操作信息。未知结果沿用原请求核对，输出失败可重试原按钮而不重复归档。

### 装修概况统计

概况使用 `_dashboard` 只读报告，展示累计装修房屋、当前在装、本月新增申请、本月结束装修，以及物业待办、等待业主处理和备案提醒。审核统一为在线审核，不拆物业/工程审核；户数与申请笔数分别标注，取消旧环比和流程/房屋类型饼图。悬停摘要或备案提醒查看统计口径。概况布局为四项摘要、装修办理趋势、当前办理状态、巡检与整改、备案风险；不嵌入装修列表或详情弹窗。办理趋势按北京时间自然月显示新增申请与实际结束装修，支持近6个月／近一年，缺月返回零值。办理状态横条与巡检整改柱图按独立指标展示申请数，不叠加为占比；点击柱条、状态坐标标签或备案提醒跳转在线审核，支持键盘聚焦入口。点击状态通过宿主已授权菜单进入在线审核，携带项目、指标和报告时刻筛选，审核页显示可清除的概况筛选标签。项目切换、刷新会清理旧报告，失败显示错误而不显示为零。后端需具备 `_dashboard`（含12个月的 `trend[{month,created,ended}]`）和 `decoration-overview-metric` 条件支持；趋势字段缺失时明确提示暂不可用。图表复用宿主Echarts组件的resize与销毁机制。

协议配置中的“二验后一次性退款金额”只读并与保证金同步；新增、编辑、切换项目及保存均使用当前保证金金额，历史两期退款字段不再提交。

PC首次、二次验收各为单一列表，按每套装修汇总最新轮次，合并待发起、待指派、待验收和历史结果。前置备案完成后才进入首验，首验通过后才进入二验；PC登记的申请可行内发起或失败重提，业主申请仍由业主发起，物业指派本轮验收人。未申请记录的申请日期、人员、轮次留空，不生成任务。指派入口与详情复用同一既有菜单按钮授权来源；历史各轮结果和操作轨迹保留在详情。

PC装修详情顶部摘要、申请信息、巡检与验收记录、整改复核、费用退款、备案人员信息及操作轨迹统一使用带标签的分栏信息布局，字段保留独立间距，姓名与联系电话分别展示；长文本和附件独立占行，长编号允许换行。流程导航、业务动作、历史内容及权限规则保持原契约。
