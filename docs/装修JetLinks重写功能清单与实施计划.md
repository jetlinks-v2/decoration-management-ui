# 装修 JetLinks 重写功能清单与实施计划

## 目标和已确定边界

保留通邑装修业务，迁移到 JetLinks 2.20：PC 复用 runtime-ui 宿主，移动端交付独立 H5，共用独立装修后端。本轮全面梳理 PC 配置、申请、审核、缴费、发证、巡检整改、首次验收、二次验收及退款结束的操作、状态和角色权限，按原系统逐环节核对并修复问题。H5员工、业主端参考巡更独立登录，复用SaaS认证与验证码，使用独立标签页会话；开发后启动本地装修并以多账号验证申请、审核、模拟收退款、备案、巡检整改及两次验收。不接真实资金/消息、不验APP真机、不部署生产或全量初始化菜单。本轮同时补齐上传/在线签署资料配置、自检/须知/申请/消防四类签字文书、审核图片框选批注、前后端联系方式及身份证格式校验，以及二次验收通过后按冻结总额执行一次性模拟退款。生成的文书与批注均须作为私有附件绑定申请/审核并可查看下载。收费科目采用公共目录选择契约，缺少提供方时明确不可用；项目章及非空客户房屋关系以测试环境真实公开接口验收。

实施顺序：先逐动作比对并记录证据，再修复与补行为回归，最后验证独立构建和本地多账号流程。资格直接采用基础档案有效客户房屋关系；H5校验本人，PC仍要求有效员工、应用和项目权限。不得通过移除旧access配置同时放宽这些边界。

后端落点 `property-management/modules/property-decoration/property-decoration-manager` 和 `services/property-decoration-service`。不因菜单拆服务；没有跨业务消费方时不建立 decoration-core。公共基础数据只由 property-base 持有。PC/H5 在 decoration-management-ui 同仓库，业务路由 `/decoration/**`；H5 独立构建 `dist-mobile`，默认静态路径 `/decoration-h5/`。服务身份 `property-decoration-service`，数据库 `property_decoration`，命名空间 `property-decoration`，本地默认端口 8505、集群 18505、RPC 28505；这些是本地开发配置，测试环境端口仍需发布前核验。

## 源码证据

- 原 PC：`通邑/装修管理-前端/ts-repair-ui/src/views/decorationManagement`，13 个列表/概览入口，附属弹窗和表单。
- 原业务后端：`通邑/报事报修_装修管理_承接查验_后端/ts-repair/src/main/java/com/jinke/ts/tsds` 的 `rest/decoration`、`entity/decoration`、`service/read/decoration/impl`、`service/write/decoration/impl`、`utils/decoration`；数据库升级脚本位于原后端根目录 `decoration_*.sql`。
- 已定位业主小程序：`通邑/小程序/zjmerchantapplet/src/pages.json` 引用 `page_subject/decorationApply`，其 `src/api/decorationApply.js` 实际请求原 ts-repair 的 `/repair/decoration/**`，不是把候选 ts-zjmerchantapplet 当装修后端。
- 新基础档案：`property-base-core` 的公开目录命令，`property-base-manager` 的 Customer/Relationship/House 和 ArchiveScope。稳定关系是项目 + 空间 ID + customerId + userId；不能用电话或姓名证明房屋归属。
- 参考宿主集成：收费与公共 property-base-ui 的 moduleRegistry、菜单和公共基础页面；参考巡更 mobile 的独立构建和会话传输，不复制巡更业务。

## 功能边界与顺序

| 业务切片 | 原实现依据 | 重写要求 |
| --- | --- | --- |
| 装修协议 | AgreementManagement，DecorationAgreement、SupplementaryAgreement | 项目+业态匹配；收费科目、保证金、退款与费用配置，补充协议；申请保存协议快照 |
| 动态资料/图纸 | MaterialConfig，DecorationMaterialConfig | 项目+房屋类型+装修类型；启用/必填/排序、上传或签署来源；申请冻结配置快照 |
| 检查配置 | CheckConfig，DecorationCheckConfig | 分类和检查项，scene、输入类型、选项、合格标准、图片、整改期限；配置变更不篡改历史 |
| 自检/申请 | RenovationSelfCheck、OnlineReview，owner-submit | 账号与房屋关系、施工主体、时间、自检和须知、材料与签名；同一房屋不得同时存在未结束申请 |
| 资料、图纸及押金审核 | DecorationApprovalWriteServiceImpl、DepositReviewHelper | 分项审核、批注、驳回重传；保证金必须逐申请显式审核，金额不变也要审核；缴费后禁止改价 |
| 支付/财务 | Payment、Refund、OfflineFinance | 接入前返回明确不可用；支付不能由客户端确认成功；线下单据必须真实核对项目、房屋、主体、科目、类型、金额、状态和防重复使用 |
| 装修备案证 | DecorationPermitWriteServiceImpl | 收款核验后发证；施工人员、有效期快照、打印时间、延期记录；不绕过付款门槛 |
| 装修记录 | DecorationRecord | 查询快照与全轨迹、修改计划竣工日期、填写原因手动结束；结束后拒绝新办理，保留历史 |
| 巡检 | AssignTask、InspectionRecord | 指派多个角色及各自每N天一次、有效时段；到期角色共享日期任务，独立反馈和历史，不以总次数代替周期；不得变成巡更打卡 |
| 违章与整改 | ViolationRecord，InspectionRecordWriteServiceImpl | 巡检不通过直接生成业主整改待办，业主提交后由角色复核；驳回、重提、重指派；原 PC 来源可重发整改任务；原巡查意见独立保留，逐次展示办理人、时间、意见、状态、复核角色及整改附件 |
| 首验/复验 | FirstAcceptance、SecondAcceptance | 申请须选择验收日期，提交时间/申请人/来源由服务端记录；指派不得覆盖申请元数据。多验收人独立任务、当前轮次汇总；首次全通过才可二次，失败重发保留旧轮次与日期快照；业主和管理端办理资格分开 |
| 结束/退款 | Refund、OfflineFinance | 二验通过后按冻结协议总额一次性退款，成功才自动结束；手动结束不是退款成功 |
| 统计/导出/打印 | HomeStatistics，各页 API | 与列表同授权、同项目筛选；稳定排序；附件、批量及导出不能绕过授权 |
| 系统管理 | 基础模块复用规范 | 与收费相同，加载 `property-base-ui`，不复制页面或注册装修基础菜单；沿用公共 `charging/*` 菜单与 `/property/**` API |
| H5 | 旧 page_subject/decorationApply | 申请、资料签署/上传、审核结果/重传、备案证、验收、整改、退款状态；独立入口，不加载桌面布局 |

## 权限与一致性

装前自检单独使用业主提交时的快照记录，PC 列表提供自检编号、项目、房号、提交时间、登记人、查看与删除；项目/房号模糊查询、提交时间区间和分页在服务端执行。PC 不新增自检，不将普通装修申请当作自检列表；删除只隐藏该记录，申请历史和原申请附件保持不变。业主申请提交时记录九项自检答案、自动汇总结果与包含全部自检项和手写签字的完整图片，重试不重复生成；PC新增申请也必须填写同一张自检表并签字，完整图片保存在申请快照内；现有历史申请不自动回填。查询和删除复用装修资源及统一授权范围，删除另需菜单按钮权限。

装修申请、任务、配置和自检列表统一使用 `ConditionFilter` 的 `change.filter.terms` 正式输出。`modelValue` 仅用于编辑回显，不直接查询；空区间或未选选项不会传给数据库，“包含”由组件转换成模糊查询，日期也由组件统一转换。项目、类别和页面状态约束始终独立于用户的 OR 条件。

装修概况复用宿主 Echarts，展示累计装修总户数、在装中户数及自然月环比、审批流程分布和房屋类型装修户数占比。户数按基础房屋ID去重，不累加同房多次申请；在装/完工沿用旧首页最新申请退款状态口径，手动结束不代表已退款。流程各项可能重叠，不能将其相加当作总户数。环比由后端按上海时区本月与上月自然月计算；切换/清空项目重查，旧响应不覆盖新范围，目录或统计失败明确报错，不显示虚假零值。真实装修数据为0时只确认接线和空态，非零统计结果由隔离数据库测试验证。

- 菜单动作使用装修资源；项目数据范围以基础公开命令的 AssetsHolder 授权结果为准。所有列表、详情、附件、统计、导出和动作共用同一 owning boundary。
- 租户、SaaS 会话入口、业务应用与业务项目是不同字段。服务从可信认证与应用上下文取值，拒绝通过 URL 或请求体伪造身份。调用基础命令保留 Authentication、AssetsHolder、TenantHolder。
- 基础命令扩展只暴露装修需要的有权房屋/客户关系只读快照；基础失败直接失败，不退回全量或空数组。
- 业务写入使用响应式事务、聚合版本/行锁，申请幂等键和房屋占用唯一约束；状态和轨迹原子提交。网络结果待确认先查结果，不能自动重做。
- PC 草稿与办理退出保护由模块内 `useLeaveGuard` 统一接线：抽屉关闭、项目/配置类型切换、路由离开或更新均保护未保存内容；提交中或结果待确认时阻止页面内离开，浏览器刷新/关闭显示原生离开提示。配置和任务办理页使用相同规则。
- 申请人、施工人员、审核人、验收人不能仅凭“看得到项目”互相代办。所有客户端业务数据不作为认证凭据。

## 实施与验证

1. 保留本计划、逐页对照、H5 接入定义；记录原实现缺陷与明确处理边界。
2. 独立装修服务与模型、基础公开命令、项目范围、身份关系、附件边界和配置。
3. PC 与 H5 共用申请/分项审核闭环：提交、自检/资料快照、驳回重传、金额审核、轨迹。
4. 备案、巡检、业主整改/角色复核、多轮首验/复验、手动结束；外部财务接入前保持付款/发证/退款的真实阻断。
5. 系统管理、统计、导入导出/打印，错误/空态、分页、项目切换和并发/幂等验证。
6. 独立 `mvn -pl :property-decoration-service -am verify`，检查 JAR 不含兄弟 manager 和本地私密配置；PC 类型/构建和 H5 类型/构建、行为测试。浏览器验收、真实后端权限联调和 APP 真机分别记录。

## 已发现差异与处理

- 巡检记录与违规记录分开：前者包含正常反馈，后者仅查询有违规的反馈；复用任务列表和原有受控详情，新增本地菜单入口但不自动修改远端菜单/授权。任务状态使用中文选项并提交稳定编码，增加更新时间筛选；任务类型、项目与用户自选条件分别分组，避免 OR 改变页面对象范围。
- 任务创建时保留当时的业主电话、施工单位/负责人/电话、房屋/装修类型及装修申请/计划时间快照；验收另存本轮申请日期、提交时间、申请人和来源，不能用任务创建时间冒充申请时间。历史未记录字段保持空值，不推算补造。详情只读展示检查标准、结果、附件与整改截止日期。
- PC 列表补齐现有快照字段：房屋/装修类型、分项审核结果、备案编号/申报人/打印与有效期、实际结束时间；配置按协议、材料、检查场景展示收费科目、保证金及项数。房屋类型使用公共字典解析，未知历史值保留原值；不补造公共档案中缺失的区域和人员电话。
- 装修记录的修改实际结束时间与计划竣工时间分开：实际结束可登记和纠正，保存即结束并释放占用；已结束仍可纠正日期，不清空重开，不变更结束原因或收退款事实。复用save权限、统一范围、版本和幂等。是否生效中沿用备案许可起止开区间口径；备案联系人电话从发证时有效员工档案快照，历史缺失显示空值。
- 原总状态计算把验收失败统一显示验收中，且遍历顺序可能让旧轮次影响结果（ApplicationReadServiceImpl#calculateDecorationStatus）；新实现以当前轮次与真实任务状态汇总，保留失败文案和重发历史。
- 原 `DecorationStatus.fromDescription` 对未知字符串回落 HISTORY_INIT；新枚举采用稳定 value，拒绝未知状态，显示 text。
- 原部分物理删除和通用修改端点可绕过业务生命周期；新服务仅开放受控动作与逻辑删除。
- 原小程序详情传 houseId/ownerId，旧代码也存在依靠客户端身份参数的路径；新服务以当前认证账号和基础有效关系确认业主，不信任该参数。
- 原财务后端引用固定收费科目兜底；新接口未建立前不照搬旧 ID，不宣称缴费成功。
- 检查配置恢复原PC的19列Excel导入与模板下载，保留分类/小项排序、同分类同名合并及未导入项。主数据由当前有权项目和公共启用房屋类型字典解析；支持工作簿内浮动图片与WPS DISPIMG，拒绝外部资源和普通公式。整批校验后配置与成功收据同事务保存，图片失败补偿、配置版本冲突整批回滚；超时只读核对，显式重试沿用原文件及原请求号。依赖目录或文件服务不可用时不模拟成功。
- 备案打印独立预览和生成原开工证版式，保留房号、负责人、电话、许可编号、有效期、施工时段、13项须知和项目章；不打印宿主页面或依赖当前详情页签。项目章来自可信公共档案/文件适配器，无适配器、缺章、错归属、图片解码失败或换章时阻止登记打印，不用任意上传替代。先生成带章图片，再按原版本/请求号/章摘要登记；未知结果先只读核对，PNG下载不登记领取，设备输出重试不重复业务写入。

签署文书中的施工起止日期统一按 `Asia/Shanghai` 自然日生成，前后端逐字校验；不能按 UTC 截断导致上海零点日期提前一天。已保存的文书保留原始签署快照，不通过读时重算篡改历史。

分项审核表单绑定实际审核模型，提交须经过 Ant Design 表单的 `submit → finish` 链路；正在提交或存在未保存图片批注时不发送审核动作。回归测试使用真实 Form，避免仅模拟按钮点击掩盖表单未触发的问题。
驳回资料重传时，新资料的审核结果、批注图片、原图关联与坐标标记一并重置；旧版本意见与批注保存在历史快照，不挪用到新图。

业主首页退费入口与详情页共用一次性退款资格：二次验收通过后，按冻结的退款总额办理；未配置时退还实收保证金。首验后不开放退款。旧两期金额合并为总额，历史已退金额扣除，已有退款记录仍可查看；仅退款结算成功显示流程完成。

验收状态与运行证据保存在后端被忽略的 `.agent-runtime/decoration`；本文是业务契约，不记录开发流水。附录字段/端点证据见《装修PC-H5新旧系统功能与细节对照》。

巡检周期以计划起始日和上海自然日计算，分别保留各角色间隔；同一天合并到期角色共享办理，修正旧实现只取首个角色周期的问题。日期任务独立生成，前期未完成不阻断后期；已生成快照不被重新指派覆盖。角色选择复用认证公开只读命令和统一角色资产范围；审核、复核使用名称选择与后端校验，不接受任意角色ID。后台游标、行锁、确定性日期键、有界补发与观测契约见后端README。
